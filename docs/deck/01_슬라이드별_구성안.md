# A.X K2 A100 서빙 · 슬라이드별 구성안

본 문서는 PPT 20장(본문) + 부록 3장의 구성안이다. 장마다 제목, 핵심 메시지, 넣을 글, 넣을 그림·표, 발표자 노트, 주의, 근거 파일을 적었다.

## 사용 방법

- `figures/`의 PNG는 1920×1080(16:9) 한 장짜리 완성 슬라이드다. 제목과 각주가 그림 안에 있다.
- 쉬운 방법: 슬라이드를 비우고 PNG를 꽉 차게 넣는다. 발표자 노트에 이 문서의 "발표자 노트"를 붙인다.
- 직접 만들 때: "넣을 글"을 슬라이드 본문으로 쓰고, `tables/`의 CSV로 표·차트를 새로 그린다.
- 모든 숫자는 저장소 루트 `evidence/`(일부는 `docs/report/`)의 측정 기록에서 나왔다. 값은 조건당 1회 측정이다.
- 그림 안의 각주(측정 날짜, 리전, 연결 방식)는 지우지 않는다. 실험마다 리전과 연결 방식이 다르기 때문이다.

## 용어 약속 (모든 장에 같게 쓴다)

- **기준 A** = TP8×PP2, FP8, 노드 2대(GPU 16장). FP8 구성의 비교 기준이다.
- **기준 D** = NVFP4 TP8, 노드 1대(GPU 8장). NVFP4 구성의 비교 기준이다.
- **c1** = 한 요청씩. **c32** = 32개 동시 요청.
- **배수** = 기준 구성 대비 출력 tok/s. 1.00보다 크면 기준보다 빠르다. TPOT는 반대로 1.00보다 크면 느리다.
- **입력 1K / 8K / 32K** = 입력 토큰 약 1,024 / 8,192 / 32,768개. 출력은 1,024토큰이다.

## 2장. 배경: H100 없이 A100으로

- **그림**: `figures/s02_price-and-memory.png`
- **핵심 메시지**: A100 노드는 H100 노드의 약 3분의 1 가격이다. 대신 모델이 노드 1대에 들어가지 않는다.
- **넣을 글**
  - 시간당 소매가(영국 남부, 노드 1대 기준): A100 $40.96 · H100 $122.90. 노드 2대는 $81.92 대 $245.80이다. A100은 H100의 33%다.
  - 문제 ① 메모리: FP8 체크포인트 694 GB는 노드 1대(640 GB)보다 크다. 노드 2대에 층을 나눠 올린다.
  - 문제 ② FP8 텐서코어가 없다: A100(SM80)은 FP8 연산기가 없다. 가중치를 커널 안에서 BF16으로 펼쳐 계산한다(Marlin W8A16).
  - 문제 ③ DSA 커널이 SM90·SM100 전용이다: 인덱서와 희소 MLA를 Triton 포트로 바꿨다(vLLM PR #38476, 미병합).
  - NVFP4 체크포인트는 398 GB라서 노드 1대에 들어간다.
- **발표자 노트**: 가격은 Azure 소매가이고 2026-11-02에 조회했다. Spot과 예약 요금은 뺐다. 토큰당 비용 비교는 하지 않았다. 처리량을 같은 조건에서 맞춰 보지 않았기 때문이다.
- **주의**
  - 모델 사실: 전체 688B, 활성 33B(라우팅 8개 + 공유 1개), 라우팅 전문가 256개, 61층(밀집 1 + MoE 60). 컨텍스트 262,144(128K 기본, YaRN으로 256K).
  - 메모리 막대는 가중치만 계산했다. KV 캐시와 활성값은 별도다.
  - SKT 모델 카드는 80 GB 카드 12장 이상을 요구한다.
- **근거**: `tables/t08_prices_memory.csv`, `evidence/a100-nvfp4-single-node.json`

## 3장. 검증한 아키텍처

- **그림**: `figures/s03_architecture.png`. 옆에 `figures/s03_demo-chat-thinking.png`, `figures/s03_demo-chat-tools.png`를 작게 붙인다(화면 캡처 2장).
- **핵심 메시지**: Foundry 에이전트 → API Management 게이트웨이 → 웹앱 모델 API → GPU 순으로 호출하는 경로를 검증했다.
- **넣을 글**
  - FP8 프로필: 경로 `/v1`, 모델 이름 `ax-k2-fp8`(별칭 `skt/A.X-K2`), GPU 노드 2대, TP8×PP2.
  - NVFP4 프로필: 경로 `/models/nvfp4/v1`, 모델 이름 `ax-k2-nvfp4`, GPU 노드 1대, TP8.
  - 웹앱 모델 API는 App Service B1, Always On, Korea Central에서 돈다.
  - GPU 쪽은 AML 명령 작업(low-priority ND96amsr_A100_v4 ×2)이고, GPU가 웹앱으로 역방향 링크를 먼저 연결한다.
  - 노드 0: Ray head + vLLM API + PP 단계 0(층 0~30, TP8). 노드 1: PP 단계 1(층 31~60 + LM head, TP8).
  - 시험 범위(붉은 상자): BYOM 호출만 시험했다. Foundry 카탈로그 배포는 시험하지 않았다.
  - 운영 중 관찰(2026-10-19~20): 약 16시간 동안 역방향 링크가 8번(6건) 끊겼고 복구에 약 32~116분이 걸렸다. 원인은 Spot 회수로 추정하나 확인하지 못했다.
- **화면 캡처 설명**
  - thinking 캡처: 수학 문제에 6초 동안 생각한 뒤 답했다. 화면 표시는 첫 토큰 0.4초, 출력 399토큰, 초당 45.2토큰이다.
  - tools 캡처: 계산기 도구로 2^64−1을 계산했다. 화면 표시는 첫 토큰 0.4초, 출력 446토큰, 초당 48.7토큰, 모델 호출 2회다.
- **발표자 노트**: 고객은 Foundry 카탈로그 배포를 계획한다. 우리가 확인한 것은 BYOM으로 에이전트가 이 모델을 부른 경로까지다. 카탈로그 배포는 별도 검증이 필요하다.
- **주의**: GPU 리전은 실험마다 영국 남부 또는 이탈리아 북부다(A2 표 참고). 캡처에는 촬영 시점의 구성이 표시되지 않는다.
- **근거**: `docs/SERVING_DESIGN.md` §3, §8.6

## 4장. 엔진과 커널

- **그림**: `figures/s04_kernel-swaps.png`
- **핵심 메시지**: 공식 구현이 아니라 A100용 포트로 돌렸다. 저장 형식(FP8·NVFP4)은 그대로이고 계산 방식이 바뀌었다.
- **넣을 글**: 표 6행(구성요소 / 공식 기준 B300급 1노드 / 이번 A100 배치 / 영향)
  - 행렬곱: FP8×FP8 텐서코어 → Marlin W8A16.
  - 인덱서 점수: DeepGEMM FP8 MQA logits → Triton 커널(PR #38476).
  - 희소 MLA(키 2,048개 선택): FlashMLA·FlashInfer 희소 → Triton 희소 MLA(PR #38476, upstream 미병합).
  - KV 캐시: BF16 기본 → BF16만 사용. TP 랭크마다 복제되어 A100 16장에 673,792토큰.
  - NVFP4 전문가: W4A4 FP4 텐서코어(B200) → Marlin W4A16(vLLM #45306 전체 + #45295의 한 줄).
  - 엔진 코드: vLLM 0.23 + SKT fork → 같음 + PR 포트 + `mla_attention.py` 2줄 수정. 수정이 없으면 A100에서 서버가 죽는다.
- **발표자 노트**: 시작할 때 `apply_overlay.py`가 포트를 적용하고 SHA-256을 검사한다. NVFP4 포트와 같은 변경은 vLLM 0.24.0 이상에 이미 들어 있다. 이번에 쓴 SKT fork는 0.23.0이다.
- **주의**: 공식 구현이 아닌 포트다. 병목 위치는 프로파일링하지 않았다. 속도 차이의 원인은 구성에서 추론한 것이지 측정값이 아니다.
- **근거**: `docs/SERVING_DESIGN.md` §5c, §8.4

## 5장. TP (Tensor Parallel)

- **그림**: `figures/s05_tp.png`
- **핵심 메시지**: TP는 한 층을 GPU 8장이 나눠 계산한다. 노드 안(NVLink)에서는 빠르고, 노드를 넘기면 느려진다.
- **넣을 글**
  - 층마다 all-reduce로 부분 결과를 합친다. 그래서 NVLink가 있는 노드 안에서 쓰는 것이 기본이다.
  - 같은 GPU 16장을 TP16으로 묶으면(측정, 영국 남부, 2026-10-21): 한 요청 TPOT가 20.7 → 26.2 ms(1K, +26%), 21.5 → 26.9 ms(8K, +25%), 22.7 → 28.2 ms(32K, +24%).
  - 32개 동시 출력 tok/s: 404 → 421(×1.04), 208 → 218(×1.04), 61 → 54(×0.89).
  - KV 캐시 토큰: 673,792 → 310,080(×0.46).
- **발표자 노트**: 왼쪽 그림은 개념도다. 원인은 로그와 구조에서 읽은 해석이다. 노드를 넘는 TP에서는 custom all-reduce가 꺼진다는 로그를 확인했다. KV는 TP 랭크마다 복제되므로 용량이 줄어든다고 보지만, 프로파일링 값은 없다.
- **근거**: `tables/t01_layout_summary.csv`, `evidence/a100-expert-parallel-comparison.json`

## 6장. PP (Pipeline Parallel)

- **그림**: `figures/s06_pp.png`
- **핵심 메시지**: PP는 속도를 위한 것이 아니다. FP8 가중치 694 GB가 노드 1대(640 GB)에 들어가지 않아서 쓴다.
- **넣을 글**
  - TP8×PP2: 단계 0(노드 0, 층 0~30)과 단계 1(노드 1, 층 31~60 + LM head). 각 단계는 TP8(NVLink)이다.
  - 노드 사이로 오가는 것은 층 경계의 은닉 상태와 잔차뿐이다. 경계가 하나라서 스텝마다 한 번 건넌다.
  - 연결 속도(NCCL 측정, GPU 쌍당): InfiniBand 약 20 GB/s, TCP 약 0.33 GB/s.
  - 한 요청일 때는 한 번에 한 단계만 일한다. 요청이 여러 개면 두 단계가 겹쳐 일한다.
  - 측정(기준 A, 입력 1K): 한 요청 TPOT 20.7 ms, KV 캐시 673,792토큰, 최대 컨텍스트 262,144, 서버 시작 261초.
- **발표자 노트**: 이탈리아 북부 첫 실행은 InfiniBand를 끈 TCP였다. 영국 남부에서는 InfiniBand를 썼다. 연결 속도는 실험마다 다르다(10-03 영국 남부 InfiniBand는 약 20.6 GB/s, TCP는 약 0.35 GB/s).
- **주의**: 개념도는 측정값이 아니다.
- **근거**: `evidence/a100-expert-parallel-comparison.json`, `evidence/a100-verification-and-doc-speed.json`

## 7장. EP (Expert Parallel)

- **그림**: `figures/s07_ep.png`
- **핵심 메시지**: EP는 라우팅되는 전문가 256개를 GPU에 나눠 담는 방식이다. 이번 측정에서는 켜도 빨라지지 않았다.
- **넣을 글**
  - vLLM 0.23에는 EP 크기 옵션이 없다. `--enable-expert-parallel`은 켜는 스위치일 뿐이고, 크기는 DP × PCP × TP(파이프라인 단계 안)로 정해진다.
  - 구성별 EP 크기와 GPU당 전문가 수: TP16+EP16 = 16 / 16개, TP8×PP2+EP8 = 8(단계마다) / 32개, DP2×TP8+EP16 = 16 / 16개, NVFP4 TP8+EP8 = 8 / 32개.
  - DP가 1이면 토큰을 주고받지 않는다. 각 GPU가 자기 전문가로 모든 토큰을 계산하고, 합계를 TP 그룹에서 all-reduce한다.
  - 옮겨지는 것은 전문가뿐이다. 어텐션과 공유 전문가는 기존 TP 배치 그대로다.
  - 측정: 같은 구성에서 EP만 켜면 출력 tok/s가 5~12% 줄었다. 3쌍 × 6개 조건 모두 1.0 미만(×0.88~0.95, 18개 비교)이다.
  - DeepEP는 SM90·SM100용(9.0a·10.0a)으로만 빌드되어 A100용 커널이 없다.
- **발표자 노트**: EP 규칙은 vLLM 0.23 소스를 읽은 결과다. EP를 켜도 빨라지지 않은 이유(가장 바쁜 랭크가 속도를 정한다는 가설 등)는 측정하지 않았다. EPLB와 DeepEP는 시험하지 않았다.
- **근거**: `evidence/a100-expert-parallel-comparison.json`(`how_vllm_0_23_forms_ep`, `findings`), `tables/t02_ep_points_long.csv`

## 8장. DP (Data Parallel)

- **그림**: `figures/s08_dp.png`
- **핵심 메시지**: DP2×TP8+EP16은 어텐션을 두 벌 두고 요청을 나눠 받는다. 동시 요청이 많을 때만 앞선다.
- **넣을 글**
  - 노드마다 TP8 복제본 1개. 요청은 두 복제본이 절반씩 나눠 받는다.
  - MoE 층마다 두 노드 사이(InfiniBand)에서 토큰을 모으고(gather) 전문가를 계산한 뒤 나눠 준다(scatter). 전문가 256개를 GPU 16장이 16개씩 갖는다.
  - 측정(기준 A 대비, 입력 1K / 8K / 32K): 한 요청 TPOT ×1.99 / ×1.95 / ×1.88. 한 요청 출력 ×0.50 / ×0.54 / ×0.56. 32개 동시 출력 ×1.12 / ×1.36 / ×1.18. 32개 동시 TTFT ×0.89 / ×1.56 / ×1.00.
  - 최대 컨텍스트 238,656(기준 A는 262,144). GPU당 가중치 46.4 GiB(기준 A는 42.3).
- **발표자 노트**: 오른쪽 아래 "해석" 상자는 측정이 아니라 추정이다. 전문가·복제본별 부하를 측정하지 않았다. 컨텍스트 상한이 238,656인 이유도 측정하지 않았다.
- **주의**: 32개 동시 TTFT는 값이 섞여 있다(8K에서 ×1.56).
- **근거**: `tables/t01_layout_summary.csv`, `evidence/a100-expert-parallel-comparison.json`

## 부록 A1. 실행 명령

- **그림**: 없음. 코드 블록으로 넣는다. 셸 변수만 쓰고 실제 주소·ID는 넣지 않았다.
- **공통(vLLM 서버)**

```bash
vllm serve "$MODEL" --served-model-name axk2 --host "$BIND_ALL" --port 8000 \
  --max-model-len "$LEN" --gpu-memory-utilization "$MEM" --max-num-seqs "$SEQS" \
  --reasoning-parser deepseek_v3 --no-enable-log-requests \
  --tool-call-parser hermes --enable-auto-tool-choice --max-num-batched-tokens 8192
```

- `BIND_ALL`은 모든 네트워크 인터페이스에서 수신하는 와일드카드 주소다(IPv4 전체 수신 주소).
- EP 비교 구성은 `--scheduling-policy priority`를 더했고, FP8 EP 작업은 `LEN=-1`(자동), `SEQS=64`, `MEM=0.90`으로 돌렸다.
- **구성별 병렬 인자**

| 구성 | 추가 인자 |
|---|---|
| A TP8×PP2 | `--tensor-parallel-size 8 --pipeline-parallel-size 2 --distributed-executor-backend ray` |
| B0 TP16 | `--tensor-parallel-size 16 --pipeline-parallel-size 1 --distributed-executor-backend ray` |
| B TP16+EP16 | B0 인자 + `--enable-expert-parallel` |
| C1 TP8×PP2+EP8 | A 인자 + `--enable-expert-parallel` |
| C2 DP2×TP8+EP16 | `--tensor-parallel-size 8 --pipeline-parallel-size 1 --data-parallel-size 2 --data-parallel-size-local 1 --data-parallel-backend ray --enable-expert-parallel` |
| D NVFP4 TP8(노드 1대) | `--tensor-parallel-size 8 --pipeline-parallel-size 1 --distributed-executor-backend mp` |
| E NVFP4 TP8+EP8 | D 인자 + `--enable-expert-parallel` |

- **EAGLE3**: dense TP16, `--max-model-len 32768`, 64 시퀀스에 `--speculative-config '{"method":"eagle3","model":"$EAGLE3_DIR","num_speculative_tokens":3}'`를 더했다. CUDA graph 시작이 실패해 eager로 돌렸다.
- **batch-invariant**: 환경 변수 `VLLM_BATCH_INVARIANT=1`. 시작 실패.
- **NVFP4**: 체크포인트 `skt/A.X-K2-NVFP4`, 환경 변수 `NVFP4_SM80_PORT=1`, `--max-model-len -1`.
- **환경(EP 비교 작업)**: 노드 2대(ND96amsr_A100_v4), 이미지 `vllm/vllm-openai:v0.23.0-cu129`, `shm_size` 256g, `IB_PROBE=1`(NCCL이 InfiniBand를 고른 경우에만 서빙).
- **native 모델 디렉터리**: SKT 체크포인트에 native DSA 포트(`apply_overlay.py`, vLLM PR #38476)를 겹친 것이다.
- **벤치마크**: `vllm bench serve --dataset-name random --ignore-eos`. 입력 1K / 8K / 32K, c1은 4개 요청, c32는 64개 요청(32K는 32개), 출력 1,024토큰, 워밍업 2회는 버렸다.
- **주의**: vLLM 0.23에는 EP 크기 옵션이 없다. `--enable-expert-parallel`을 켜면 EP 크기가 DP × TP(단계 안)로 정해진다.

- A100 2노드 할당은 이탈리아 북부와 영국 남부에서만 성공했다. 가격 조회 리전은 영국 남부다.
- **표 2: 용어**
  - TP/PP/EP/DP: 텐서·파이프라인·전문가·데이터 병렬.
  - c1, c32: 동시 요청 1개, 32개. TPOT: 토큰 1개를 만드는 데 걸리는 시간(중앙값). TTFT: 첫 토큰까지 걸리는 시간.
  - KV 캐시: 이전 토큰의 어텐션 상태를 저장하는 메모리. 풀이 작으면 긴 요청을 동시에 많이 받지 못한다.
  - CUDA graph, eager: 미리 기록한 GPU 작업을 재생하는 방식과 하나씩 실행하는 방식.
  - NIAH(needle): 긴 문맥 속에 숨긴 코드를 찾는 시험.
  - native, dense: DSA 희소 어텐션을 쓰는 방식, 희소 선택 없이 전체를 보는 방식.
  - Marlin W8A16, W4A16: 가중치 8비트·4비트, 활성값 16비트로 계산하는 커널.
  - NVLink, InfiniBand(IB), TCP: 노드 안 연결, 노드 사이 고속 연결, 일반 네트워크.
- **측정 방법**: `vllm bench serve --dataset-name random --ignore-eos`, 입력 1K / 8K / 32K, 출력 1,024토큰, 워밍업 2회 제외, 조건당 1회 측정, 프로파일링 없음.
- **측정하지 않은 것**: EPLB, DeepEP, c32 초과 동시성, 32K 초과 컨텍스트에서의 EP 비교, Foundry 카탈로그 배포, 토큰당 비용.
