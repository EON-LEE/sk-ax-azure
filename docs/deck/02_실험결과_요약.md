## 2. 구성 7개 결과 (2026-10-21, 영국 남부)

배수는 기준 구성 대비 출력 tok/s다. FP8 5구성은 A(TP8×PP2), NVFP4 2구성은 D(NVFP4 TP8)가 기준이다. 입력은 1K / 8K / 32K 순이다. 파일: `tables/t01_layout_summary.csv`.

| 구성 | GPU | 시작(초) | KV 토큰 | 32K·c32 동시 | c1 출력 | c1 TPOT 배수 | c32 출력 |
|---|---|---|---|---|---|---|---|
| A TP8×PP2 | 16 | 261 | 673,792 | 20 | 47.5 / 41.9 / 31.9 tok/s | 20.7 / 21.5 / 22.7 ms | 404 / 208 / 61 tok/s |
| B0 TP16 | 16 | 251 | 310,080 | 9 | ×0.79 / 0.82 / 0.77 | ×1.26 / 1.25 / 1.24 | ×1.04 / 1.04 / 0.89 |
| B TP16+EP16 | 16 | 231 | 309,376 | 9 | ×0.70 / 0.72 / 0.70 | ×1.44 / 1.43 / 1.40 | ×0.98 / 0.98 / 0.83 |
| C1 TP8×PP2+EP8 | 16 | 151 | 673,216 | 20 | ×0.88 / 0.89 / 0.91 | ×1.14 / 1.13 / 1.12 | ×0.92 / 0.92 / 0.92 |
| C2 DP2×TP8+EP16 | 16 | 221 | 238,720 + 238,656 | 14 | ×0.50 / 0.54 / 0.56 | ×1.99 / 1.95 / 1.88 | ×1.12 / 1.36 / 1.18 |
| D NVFP4 TP8 | 8 | 442 | 254,016 | 7 | 48.3 / 42.4 / 27.3 tok/s | 20.4 / 21.1 / 22.4 ms | 445 / 188 / 51 tok/s |
| E NVFP4 TP8+EP8 | 8 | 312 | 253,120 | 7 | ×0.93 / 0.93 / 0.93 | ×1.08 / 1.08 / 1.08 | ×0.95 / 0.93 / 0.94 |

- 7구성 모두 기능 시험 4/4, 도구 시험 9/9, CUDA graph 사용, 코드 수정 없이 시작했다.
- 기준 A: c1 TTFT 346 ms / 2.47 s / 8.86 s, c32 TTFT 6.2 s / 9.8 s / 213 s. GPU당 가중치 42.3 GiB, KV 25.0 GiB.

- D 대비 A: c1 ×1.02 / 1.01 / 0.86, c32 ×1.10 / 0.90 / 0.83.

## 3. 핵심 발견 (측정 사실)

1. **EP만 켜면 느려졌다.** 같은 구성에서 EP 켬/끔 18개 비교가 모두 1.0 미만이다(×0.877~0.947, 5.3%~12.3%). 표시값은 ×0.88~0.95다.
2. **한 요청은 TP8×PP2(A)가 가장 빠르다.** FP8 5구성 중 세 입력 모두 최고다. NVFP4 TP8(D)은 GPU 8장으로 비슷한 수준(1K 48.3 대 47.5 tok/s)이다.
3. **동시 32개는 DP2×TP8+EP16(C2)만 기준을 앞선다**(×1.12~1.36). 대신 한 요청은 ×0.50~0.56이고 컨텍스트 상한은 238,656이다. c32 TTFT는 입력에 따라 ×0.89 / 1.56 / 1.00으로 섞여 있다.
4. **KV 용량은 구성에 따라 달라진다.** A·C1은 약 67만 토큰, TP16 계열은 약 31만 토큰(×0.46), C2는 노드마다 약 24만 토큰, NVFP4는 약 25만 토큰이다.
5. **서버 시작 시간**: 가장 빠른 것은 C1 151초, 가장 느린 것은 D 442초다.
6. **dense는 native보다 빠르나 긴 컨텍스트에서 실패한다.** 출력 tok/s ×1.11~1.64(이탈리아 북부, TCP, 10개 조건), needle은 128K·256K에서 dense 0/3, native 3/3(영국 남부, InfiniBand).
7. **EAGLE3는 A100에서 이득을 확인하지 못했다.** CUDA graph 시작이 실패해 eager로 돌렸다. eager EAGLE3는 CUDA graph를 쓴 일반 TP16의 ×0.19~0.23이다(수락 1.046토큰/스텝). 이 비율은 eager 손실과 투기 디코딩 동작이 섞인 값이다.
8. **batch-invariant 모드는 시작 실패**, DeepEP는 A100용 커널이 없다(pplx·naive는 vLLM 0.23에서 제거).
9. **2층 log-prob**: 14,618 위치(안쪽 7,356 + 바깥쪽 7,262)에서 top-1 일치율은 세 구성 모두 97~98%다. 바깥쪽 평균 |Δ|는 dense 0.0123, native 0.0111, native PP2 0.0115다. 앞 2층만 본 결과다.
10. **정확도(부분 실행)**: AIME26 100.0(10/30문항), KoBALT 74.3, CLIcK 85.5, IFBench 78.6. 공개값(97.1 / 73.0 / 91.6 / 75.9)과 같은 평가 설정인지는 확인하지 않았다.

## 4. 해석 (측정하지 않았다)

아래는 구조와 로그에서 읽은 추정이다. 슬라이드에 쓸 때는 "추정"이라고 밝힌다.

- EP를 켜도 빨라지지 않는 이유(가장 바쁜 랭크가 속도를 정한다는 가설).
- DP2×TP8에서 한 요청이 느리고 동시 요청이 빠른 이유.
- TP16의 TPOT가 늘어난 이유(노드를 넘는 all-reduce, custom all-reduce 꺼짐 로그는 확인).
- TP16에서 KV가 0.46배가 된 이유(MLA KV가 TP 랭크마다 복제).
- DP2의 컨텍스트 상한이 238,656인 이유.
- dense가 빠른 이유(희소 선택을 건너뜀)와 긴 컨텍스트에서 실패하는 이유.
- EAGLE3 수락률이 낮은 이유.

## 5. 한계와 주의

- 공식 구현이 아닌 포트(Marlin W8A16·W4A16, Triton 인덱서·희소 MLA)로 돌렸다. 병목 위치는 프로파일링하지 않았다.
- 조건당 1회 측정이다. 반복·신뢰구간이 없다.
- 정확도 평가는 부분 실행이다. AIME26은 10문항이 모두 정답이라 신뢰구간이 0으로 붕괴한다. CLIcK 공개값 91.6은 구간 상한(91.55)보다 0.05%p 높다.
- 2층 log-prob은 전체 모델 정확도가 아니다. 원자료 시계열은 `evidence/a100-native-2layer-logprob-series.json`에 있다.
- NVFP4 대 FP8은 서로 다른 할당과 날짜가 섞인 교차 비교다. NVFP4의 정확도 동등성은 측정하지 않았다(기능·도구·needle만). "복제본 2개면 약 2배"는 추정이다.
- Foundry 카탈로그 배포는 시험하지 않았다. BYOM 호출 경로만 검증했다.
- 토큰당 비용은 비교하지 않았다.
- 역방향 링크는 2026-10-19~20 약 16시간 동안 8번(6건) 끊겼다. 복구에 약 32~116분이 걸렸다. Spot 회수로 추정하나 확인하지 못했다.
- dense TP16 대 TP8×PP2(10-03, 모드 dense, 총 처리량)와 10-21 native EP 작업(출력 tok/s)은 모드와 지표가 다르다.
- 검증 JSON의 `nvfp4_checkpoint` "불가" 항목은 낡은 주장이다. 2026-10-04 작업에서 정정되었다.
- 측정하지 않은 항목: EPLB, DeepEP, c32 초과 동시성, 32K 초과 컨텍스트에서의 EP 비교, 60K~128K에서의 dense.
